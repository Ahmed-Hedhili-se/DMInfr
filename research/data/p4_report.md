# Phase 4 (SQ4): does threshold decoding make routing fragility better or worse?

Generated by `python -m research.sq4` (tables below). Spend: $1.07 (one
container, 2 arms × 1319 questions, A100-40GB).

## Summary

- **Slightly worse, and the difference just clears the noise floor.**
  - On the 684 questions uncapped under both schedules, fp32 routing changes
    **26.2% [23.0, 29.6]** of strict answers under threshold decoding,
    against **21.8% [18.9, 25.0]** under the fixed schedule.
  - Paired over the same questions: 109 churn only under threshold and 79
    only under fixed, McNemar p = 0.034. On all 1319: 40.4% vs 35.4%,
    p = 0.002.
  - A +4–5 point increase at p ≈ 0.03 from one comparison is a modest
    result, not a strong one.
- **Threshold decoding runs fewer steps but churns more.**
  - It ran 62% of the fixed schedule's denoising steps, so fewer routing
    decisions, yet churned more.
  - Its trajectories also diverge earlier: median first-divergence step 3,
    against 4 for fixed.
  - This matches Phase 2: churn follows whether and how early the
    trajectory moves, not the number of routing flips.
  - A plausible mechanism, not tested here: threshold decoding commits
    several tokens per step by confidence, so a confidence perturbation
    changes both *which* and *how many* tokens commit.
- **Accuracy is unchanged within each schedule.**
  - Fixed: 75.7 → 76.6%, p = 0.38. Threshold: 74.2 → 74.7%, p = 0.73.
  - Between schedules the control moves 75.7 → 74.2% (p = 0.21), not
    resolved.
- **The schedule switch is itself a perturbation of the same size.**
  - Fixed control vs threshold control changes 23.2% [20.2, 26.6] of strict
    answers on the 684.
- **No decoding collapse in any arm** (0/1319 in all four). The longest
  repeated-token run is 7. This config uses 32 steps per 32-token block
  (ratio 1.0), the setting §8c found removes the collapse. The §4d failures
  (ratio 0.5, 1024 tokens, block 64) are not reproduced or tested here.
- **Agreement with the repo:** the threshold pair disagrees on correctness
  for 214/1319 questions (16.2%), in line with `h100x2_bench.md` §9e's
  167/1000 (16.7%). That was n=1000, `steps=1024 block_length=64`, threshold
  0.9/0.4, on an H100. The fixed pair's correctness discordance is 13.9%.

**Caveats.**
- The fixed and threshold pairs ran in different containers. Phase 2's
  cross-container check (64/64 identical) supports pairing them, but there
  was no sentinel in the Phase 4 container.
- Under threshold decoding a block can finish before its 32 steps, so
  step-indexed divergence there is an upper bound on elapsed forward passes.
- The capped fraction rises from 39.0% to 41.3% under threshold decoding.

## SQ4: threshold decoding (0.9 / 0.4) vs the fixed schedule

Setup: n=1319 (full GSM8K test set, seed-42 order), A100-40GB, `max_tokens=256 block_length=32 steps=256` (32 steps per block = block length, ratio 1.0), B=32, identical batches in all four arms. Fixed pair from Phase 2 (container A); threshold pair from Phase 4. Threshold = `select_transfer_indices_hierarchy`, confidence 0.9, low 0.4.

Denoising steps actually run (control, summed over 1319 questions in batches): fixed 10,752 step passes, threshold 6,672 (62.1% of fixed).

Capped in control: fixed 514/1319 (39.0%), threshold 545/1319 (41.3%). Uncapped under both: 684.

### Churn of each pair (control vs fp32_all)

| population | fixed: strict churn [95% CI] | threshold: strict churn [95% CI] | churn only fixed | churn only threshold | McNemar p (fixed vs threshold churn) |
|---|---:|---:|---:|---:|---:|
| uncapped under both (primary) (n=684) | 21.8 [18.9, 25.0] | 26.2 [23.0, 29.6] | 79 | 109 | 0.0341 |
| all 1319 (n=1319) | 35.4 [32.9, 38.0] | 40.4 [37.8, 43.1] | 194 | 260 | 0.00225 |

- fixed, own uncapped (n=805): 24.6% [21.7, 27.7]

- threshold, own uncapped (n=774): 28.8% [25.7, 32.1]
